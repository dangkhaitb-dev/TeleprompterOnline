# Project instructions

## Project profile

SolPrompter is a web teleprompter built with Vite, Eleventy (11ty), and
vanilla JavaScript ES modules. There is no frontend framework. Preserve that
stack unless the user explicitly requests an architectural change.

For implementation, bug-fix, refactor, frontend, test, or code-review work in
this repository, use the repo skill `solprompter-development` from
`.agents/skills/solprompter-development/`. Its workflow and this file are the
Codex equivalents of the former Claude project workflow. If the skill is not
discoverable in the current session, follow this file directly.

## Commands

```bash
npm run dev
npm run build
npm run lint
npm run lint:js
npm run lint:css
npm test
npx vitest run src/script/path/to/file.test.js
```

Use `npx --no-install` for targeted lint commands so verification does not
silently install packages.

## Planning gate

Before editing, present an implementation plan and wait for explicit user
approval when a task does any of the following:

- changes three or more files;
- changes architecture or layer boundaries;
- adds a feature rather than a small fix;
- refactors existing code;
- changes an API contract or data model.

Use Codex plan tracking for the approved plan. Small fixes limited to one or
two files, typo corrections, and contained style changes may proceed directly.

When the user has already approved a concrete plan or explicitly asks Codex to
execute an already-defined migration, do not request duplicate approval.

## Core architecture

```text
src/script/
  constants/api-endpoints.js
  constants/events.js
  http/errors.js
  http/http-client.js
  environment.js
  libs/firebase/
  services/[name].service.js
  features/[name]/
    [name].model.js
    [name].logic.js
    [name].ui.js
  main.js
```

Follow the dependency direction:

```text
constants -> http -> service -> model -> logic -> ui
```

- Higher layers must not be imported by lower layers.
- UI is the only layer that may access the DOM.
- Services call `http-client` and return raw data; they do not contain UI or
  mapping logic.
- Models expose pure `toXxx(raw)` mapping functions and define app-facing data
  shapes.
- Logic orchestrates services and models without touching the DOM.
- UI owns DOM events and user-facing error handling and exports `initXxxUI()`.
- Wire feature UI from `main.js`.

### Add an API

1. Add the endpoint specification to `ENDPOINTS` in
   `src/script/constants/api-endpoints.js`.
2. Add a service function in `src/script/services/[name].service.js`.
3. Keep the service limited to an `http.get`/`http.post` call and raw data.

### Add a feature

Create `features/[name]/[name].model.js`, `[name].logic.js`, and
`[name].ui.js`, then call `initXxxUI()` from `main.js`.

## Project invariants

- Do not add `Co-Authored-By` to commits.
- Never bypass repository hooks with `git commit --no-verify` or
  `git commit -n`.
- Backend field changes belong in the model mapper, not consumers.
- Let service and logic errors bubble naturally; handle them in UI.
- Read timeout values from `environment.api.timeout`; do not hardcode
  milliseconds.
- Declare CustomEvent names in `src/script/constants/events.js`; never use
  event-name string literals.
- Do not use `window.__*` as cross-module communication. Use static imports.
- Feature code must not call `localStorage` or `sessionStorage` directly. Put
  storage access behind `src/script/utils/`.
- Do not use `alert()`, `confirm()`, or `prompt()`. Use a custom popup.
- Overlay backgrounds may be darkened with `rgba(...)`; never add
  `backdrop-filter: blur()`.
- Use design tokens from `src/styles/tokens.css` for colors, spacing, and
  typography.
- Mobile `input` and `textarea` font sizes must be at least 16px.

### Recording and teleprompter details

- Results from `listAllRecordings` and `listByWorkspace` may contain
  `blob: null` with `hasBytes: true`. Call `ensureRecordingBlob` in the service
  layer or `loadRecordingBlob` in `workspaces.logic` before media access.
- Use `getVideoThumbnail(id, blob)` rather than calling
  `extractVideoThumbnail` directly. It memoizes by id and limits concurrent
  decoders.
- Cross-tab teleprompter sync currently shows only a desktop edit-view
  "Content updated" badge.
- Cross-tab sync tracks content (`scriptHtml`, `scriptText`, and inline style),
  not settings.
- The implementation lives in `utils/cross-tab-sync.js` and
  `features/teleprompter/collab/`.
- `persistSharedState` must call `notifyLocalWrite()` after saving content so
  the stale badge is re-baselined.

## HTML templates

Root HTML files are generated by Eleventy and must not be edited directly.

- Layout: `_templates/_includes/base.njk`
- Pages: `_templates/pages/*.njk`
- Page text/data: `_templates/_data/pages/<page>/en.json`

Do not hardcode page copy in Nunjucks templates.

For a new single-language page:

1. Add `_templates/pages/<key>.njk`.
2. Set `layout`, `permalink: /<key>.html`, `pageKey`, and `lang`.
3. Add `_templates/_data/pages/<key>/en.json`.
4. Reuse navigation/footer chrome from `i18nPages['index']['en']`.
5. Do not add the page to `indexPages.cjs`; that file only paginates the
   multilingual index.
6. Use canonical `/<key>`.

`partials/json-ld.njk` belongs only to the index schema and assumes index data.
For structured data on another page, create a guarded page-specific partial
and include it from the layout.

After template changes, run the build so generated HTML, sitemap, and Vite
inputs are refreshed.

## Frontend and responsive design

- Build mobile-first. Base styles target small screens; add complexity with
  `min-width` media queries.
- Support at least 320px, 390px, 768px, 1024px, and 1440px viewports.
- Never ship horizontal page overflow.
- On mobile, preserve this reading order: section heading, primary product
  visual, supporting content, secondary details.
- Do not force unequal content into equal-height side-by-side cards. Stack it
  on small screens and use asymmetric layouts only when space permits.
- Keep touch targets at least 44px where practical and preserve visible
  keyboard focus.
- Use the existing system font stack. Do not add external fonts unless the user
  explicitly requests one.
- Choose a specific visual direction and intentional hierarchy. Avoid generic
  template layouts, uniform card grids, decorative gradients without purpose,
  and unmodified library defaults.
- Verify the complete affected page on mobile, tablet, and desktop before
  finishing visual work.

## Development workflow

1. Inspect relevant code, tests, git status, and existing conventions.
2. State assumptions that materially affect the solution.
3. Define observable acceptance criteria.
4. Prefer the smallest solution that satisfies those criteria.
5. For new features and reproducible bugs, write or identify the failing test
   first when practical, implement the minimum fix, then refactor only if
   needed.
6. Keep changes surgical. Do not improve unrelated code, and remove only
   orphaned code created by the current change.
7. Run targeted checks while iterating and proportional final verification.
8. Review the final diff for correctness, security, regressions, and project
   convention compliance.

recent-turn fork and pass task-local context explicitly. Do not combine a named
custom agent type with a full-history fork.

## Security baseline

- Never hardcode credentials, tokens, or secrets.
- Validate untrusted input at system boundaries.
- Sanitize any user-controlled HTML before injection.
- Verify authentication and authorization when touching protected flows.
- Do not leak sensitive context in UI errors or logs.
- Use CSRF protection and rate limiting where server-side state-changing
  endpoints exist.
- Treat exposed secrets as an incident: stop, report the exposure, rotate the
  secret, and inspect for similar occurrences.

## Verification and review

- The repo-local Codex PreToolUse hook blocks any `git commit` command that
  contains `--no-verify` or `-n`.
- The PostToolUse hook lints edited JS/CSS files and blocks on lint errors.
- The Stop hook requests one focused self-review after JS changes.
- Run broader checks yourself when the change scope warrants them; hooks are
  guardrails, not a substitute for verification.
- Review findings must lead with concrete, actionable issues and file
  references. Ignore style-only commentary already enforced by lint.
- Before completion, inspect `git diff` and make sure unrelated user changes
  remain untouched.
